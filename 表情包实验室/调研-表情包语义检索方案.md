## 1. 开源同类项目的检索实现细节

### 1.1 anka-afk/astrbot_plugin_meme_manager（566★，MIT，持续更新至 2026-11）

这是四个项目中最成熟、与本项目需求最接近的参考。核心链路：**LLM 生成简短中文检索词 → AstrBot EmbeddingProvider 向量化 → faiss-cpu 余弦 TopK → min_score 阈值过滤**。

**向量索引（backend/semantic/index.py）**
- 依赖只有 `faiss-cpu`（requirements.txt），使用 `faiss.IndexFlatIP` + `IndexIDMap2`，写入前对向量矩阵执行 `faiss.normalize_L2`，即**内积=余弦相似度**检索。
- 索引落盘为 `index-<uuid>.faiss` + `index_manifest.json`；manifest 记录 `embedding_provider_id / embedding_model / embedding_dimension / distance: cosine / item_count / items(faiss_id↔entry_id, text_hash)`。
- **索引失效机制**：查询时校验 manifest 的 provider/model/dimension 与当前 embedding 提供方是否一致，不一致直接返回空并提示重建；支持增量更新时从旧索引 `reconstruct()` 复用未变更向量（按 text_hash 匹配），只对新增/变更图片重新 embed。
- 检索 `search_index()`：query 向量化后 `index.search(query_vector, result_limit)`，逐个校验候选图片文件仍存在且 sha256 未变（防目录被手动改），不足时扩大 `result_limit` 重搜；`min_score` 默认 **0.25**（余弦），`top_k` 默认 5。
- Windows 中文路径兼容：faiss 的 C++ 文件 API 打不开 Unicode 路径，作者用 `faiss.PyCallbackIOReader/Writer` 从 Python 文件对象读写绕过（v5.4.1 修复记录）。

**query 构造（backend/semantic/query_builder.py）**
- 不直接拿用户消息当 query。`build_semantic_query()` 的提示词（原文）：
  > "任务：把已有回复的表达意图压缩为表情图片检索词，不回答用户。用简短短语概括回复者的态度、情绪、用途或动作，保留对象关系，例如安慰对方与嘲笑对方、自嘲与指责他人应当区分。依据准备发送的回复，而非直接照搬用户的情绪……只输出 JSON：{\"query\":\"简短检索词\"}"
- 即：**用"准备发送的 AI 回复"生成检索词**，而不是用户消息；失败时回退到回复原文（`reply_text` 模式）。
- 多包检索 `search_memes_multi_pack()`：跨多个表情包分别查各自 FAISS 索引，合并按分数排序取全局 top_k，并做 entry 去重。

**选图决策层**：标签粒度分"分类级（主模型自选/辅助模型）"与"图片级（语义检索）"两档；语义索引未就绪时自动回退分类随机；提供 `send_meme` / `search_memes` / `preview_memes` 工具给主模型调用；`search_memes` 结果作为 tool 返回给模型，由模型挑一张。
- 来源：https://github.com/anka-afk/astrbot_plugin_meme_manager （README、requirements.txt、backend/semantic/{index,query,query_builder}.py 源码）

### 1.2 TheD0ubleC/StickerSelector（33★，GPL-3.0，2026-01 有更新）

独立 Python FastAPI 服务。链路：**标签文本 → m3e/BGE 向量化 → SQLite 存 float32 blob → 内存矩阵乘精确 TopK →（可选）bge-reranker 精排 → softmax 映射 fit_rate**。

- **embedding 模型（sticker_service/model_state.py、embedding_models.py、embed_m3e.py）**：可选档位
  - `moka-ai/m3e-small`（默认，mean pooling + L2 归一化，fp32/fp16）
  - `BAAI/bge-small-zh-v1.5`、`BAAI/bge-large-zh-v1.5`（CLS pooling，fp32/fp16）
  - `bge-large-zh-v1.5 + BAAI/bge-reranker-large`（两阶段：向量召回 recall_topk 默认 20，cross-encoder 精排）
- **存储（db.py）**：SQLite 三表 series/batch/sticker；`sticker.emb_blob` 存 `np.float32.tobytes()`，`emb_dim` 记维度；另有 `data_runtime/embeddings/<id>.npy` 本地副本。开启 WAL。
- **检索（indexer.py）**：`StickerIndex.refresh()` 启动/变更时从 SQLite 拉全部启用向量 `np.stack` 成 `[N,D]` 矩阵；查询 `scores = self._embs @ q` 后过滤 enabled/series 再排序取 TopK。**纯暴力精确检索，无 ANN**——对几千~几万张完全够用。
- **匹配文本**：query 和文档都是"标签拼接文本"（`tags_to_text(tags)`），不是图片视觉内容——标签来自人工或 LLM 打标。
- **打分展示**：cosine 相似度经 `softmax(scores * 55)` 映射成 0~100 的 `fit_rate`，`match_rate = cosine*100`。
- 来源：https://github.com/TheD0ubleC/StickerSelector （sticker_service/ 源码）

### 1.3 SucRoseZT/astrbot_plugin_sticker_kit（4★，MIT，2026-11 活跃）

**纯本地加权计分检索，无向量模型**，但工程细节非常值得抄。

- **标注体系**：LLM 视觉打标，受控词表——`_EMOTION_VOCAB`（开心/委屈/无语…约 40 个主情绪+次情绪）、`_SCENE_VOCAB`（收到/比爱心/拥抱/敬礼…用途动作词，v1.12 新增）、`tags` 画面词、名称、描述、置信度；`ban_english_emotion` 把 happy/sad 等英文词映射回中文受控词。
- **query 构造**：快速通道让 AI 在回复末尾输出 `<sticker>{"query":"情绪词 画面词"}</sticker>`，本地解析；口语别名归并表 `_ALIAS`（呆萌→卖萌、心累→疲惫…）、`_SCENE_ALIAS`（比心→比爱心、抱抱→拥抱…）。
- **分词**：无空格中文长串（如"蓝发女仆眨眼"）不做 2-gram，而是**按库存标签词表做正向最大匹配切词**（切出 ≥2 词才采用），词典来自库存本身。
- **计分（v1.6+ 重写）**：每个字段取"最佳命中质量"（0~1，精确=1.0、别名=1.0、双向包含=0.9、difflib/Jaccard 模糊 ≥0.62 才算）后加权求和：
  - `score = _W_SCENE*best(scene) + _W_PRIMARY*best(主情绪) + _W_SECONDARY*best(次情绪) + _W_TAGS*best_tag + _W_TAG_EXTRA*min(covered-1,2) + _W_INTENTS*best(intents) + _W_NAME*best(name) + _W_DESC*best(desc) + _W_VTEXT*best(可见文字)`
  - 每字段取 max 不累加，防止"标签多=分高"；README 明确"主情绪权重最高、名称权重最低（0.5）"。
- **门槛**：`min_score`（最低匹配分）与 `min_margin`（第一名需领先第二名一定倍数）可配置，也可按配图频档（很少/适中/较多/每条都发）经 `_AUTO_GATE` 自动放宽；强命中（`_STRONG_SCORE`）在分数接近的候选池内随机挑一张避免总发同一张；`blocked_tags`（威胁/血腥…）命中即拦截，除非 query 本身提到。
- **性能**：作者实测 500 张库单次检索从 34~65ms 优化到 **3~9ms**（无共同字预筛、一次遍历同时算 best 与覆盖数）。
- **成本控制**：`sticker_search` 工具结果会永久留在对话历史里逐轮计费，因此按档位裁剪返回字段（精简=仅 id+名称+主情绪，4 条仅约 318 token）；快速通道零检索 token。
- 来源：https://github.com/SucRoseZT/astrbot_plugin_sticker_kit （README、main.py 源码）

### 1.4 QingchenWait/astrbot_plugin_smart_imagechat_hub（35★，GPL-3.0）

- **三档延迟策略**（表情包检索模式配置）：
  1. `bot_reply_serial`：先让 bot 生成回复，再按回复内容检索表情包——语境最准，延迟最高；
  2. `user_message_parallel`：按用户发言在主回复生成前后台并发检索——更快；
  3. `user_message_fast_prefilter`：按发言内容**本地标签+强语义命中预筛精排**、小规模并发，主回复完成时若检索未结束则取消，仅高置信命中时用本地兜底候选——最快。
- **置信度门槛**：LLM 分析输出 confidence，低于 `最低匹配置信度`（默认 **0.45**）视为未找到，不发图。
- **标签生成**：上传后由"默认图片转述模型"（视觉 LLM）自动生成多维度特征标签（图像类别、人物特征、身材、情绪、动作、图片中的文字），标签存插件配置 `image_tags`。
- 来源：https://github.com/QingchenWait/astrbot_plugin_smart_imagechat_hub （README）

### 1.5 对本项目最有用的共同结论

1. **query 不该是用户原话**：meme_manager 与 sticker_kit 都让 LLM 基于"将发送的回复/语境"生成 2~5 个词的短检索词；这比直接 embed 长对话更准且向量更稳。
2. **1.9 万规模不需要 ANN 也能很快**：StickerSelector 用全量矩阵乘、sticker_kit 用纯 Python 计分都能做到个位数~几十毫秒。向量法下 19000×512 float32 ≈ 39MB，内存点积一次 <10ms。
3. **门槛+margin 是防"硬塞图"的关键**：两项目都用 min_score + 领先幅度（或置信度阈值）决定"发不发"，低于就纯文字兜底。
4. **索引与元数据一致性校验**（sha256/manifest 签名）值得照抄，避免图库手动变更后检索到失效条目。

| **阿里 text-embedding-v4 / 硅基流动 bge-m3 / 智谱 embedding-3**（API） | - | - | - | API 网络延迟 | API | 定价页动态加载，本次**未能验证**具体单价；量级参考：embedding API 普遍为每百万 token 几毛~几元人民币，1.9 万张短文本一次性向量化成本通常 <1 元人民币（估算，非报价） |

**速度参考锚点**：StickerSelector 实测在其服务内跑 m3e-small/bge 系批量向量化数百万 token 级库；sticker_kit 的 LLM 打标链路实测单张 3.6s（含视觉模型）。**本项目 1.9 万张是一次性离线索引**，即使 bge-m3 也就分钟级；真正要压的是在线 query 向量化延迟——512/768 维 BERT 系模型单条 CPU 推理通常 <10ms（ONNX int8 更快），聊天链路完全可接受。精确到本机硬件的毫秒数**未能验证**（需实测）。

**结论**：
- 本地 CPU、Node 进程内：**bge-small-zh-v1.5（512 维）** 是延迟/效果/体积平衡点；预算允许可上 bge-base-zh-v1.5。
- 若坚持"英文描述库 + 中文 query"且不想重写描述：**bge-m3**（跨语言）或 Qwen3-Embedding-0.6B（更强但更重）。
- 纯 API 路线：延迟（网络 RTT 通常 50~300ms）与隐私是主要代价，1.9 万张离线建库成本可忽略。

## 3. Node.js 侧向量存储/检索方案对比

| 方案 | 形态 | 适配 1.9 万张 | 优点 | 缺点 | 维护状态（2026-11 查证） |
|---|---|---|---|---|---|
| **pgvector** | Postgres 扩展（v0.8.7） | ✅ 绰绰有余 | 与现有 Postgres 同库、ACID、SQL 过滤（情绪/场景/风格/关系阶段直接 WHERE）、HNSW/IVFFlat 索引、halfvec 减半存储、iterative scan 解决过滤召回、官方 hybrid search（全文+RRF/cross-encoder）、pgvector-node 客户端 | 需在 Postgres 服务端装扩展；Windows 裸机要 VS 编译或用 Docker/conda；连接走网络有一次 RTT | 极活跃：23.7k★，2026-11-18 仍有提交 |
| **内存矩阵（自研，学 StickerSelector）** | Node 进程内 Float32Array [N,D] | ✅ 39MB(512d)/78MB(1024d) | 零依赖、最快（点积 <10ms）、无跨进程 RTT；向量可存 SQLite/文件/Postgres 任一 | 重启需重载或重建；多实例需各自加载；无持久索引结构；过滤逻辑自己写 | 自己维护，无外部风险 |
| **sqlite-vec** | SQLite 扩展（C，单文件） | ✅（暴力 KNN） | 零服务、单文件、better-sqlite3 可加载；适合嵌入式/本地优先 | 当前无 ANN 索引，暴力扫描；大数据量弱；Node 侧需处理扩展加载 | 活跃：8.3k★（2026-05 最后 push，issues 252 开放） |
| **faiss-node** | Node 原生绑定（N-API） | ✅ | 能力对标 faiss（IndexFlatIP/HNSW 可选） | **基本停更**（最后 push 2023-10，140★，20 open issues）；Windows node-gyp 构建麻烦 | 不建议新项目依赖 |
| **usearch** | C++ 核心 + 多语言绑定（JS/WASM） | ✅ | HNSW 高性能、内存占用小、支持 fp16/int8 量化、JS 绑定存在 | Node 生态案例少；仍是原生依赖需构建/预编译产物匹配 | 活跃：4.4k★，2026-11 仍有提交 |
| **hnswlib** | C++/Python 头文件库 | - | 经典 HNSW 参考实现 | **无官方 Node 绑定** | 活跃（5.4k★）但与 Node 无关 |
| （对照）**meme_manager 的 faiss-cpu** | Python 生态 | - | IndexFlatIP 精确检索，简单可靠 | Python 专用，Node 项目只能借鉴思路 | faiss 本体活跃 |

**结论**：
- 已有 PostgreSQL ⇒ **首选 pgvector**。1.9 万行即使不上 HNSW、纯精确 `ORDER BY embedding <=> $1 LIMIT k` 也是毫秒~十几毫秒级（19000×512 次乘加 ≈ 9.7M FLOPs，Postgres 单核毫秒级可完成；精确数值需实测，**未能验证**）；上 HNSW 后更快且支持 `hnsw.ef_search` 调召回。
- 想要**零 Postgres 改动、最低延迟** ⇒ **进程内 Float32 矩阵 + 点积**（向量本体继续存 Postgres 一列 bytea/float8[] 或 JSON，启动时载入）。这同时规避了 faiss-node 停更与 sqlite-vec 暴力扫描的短板，且过滤逻辑（情绪标签 OR 场景包含）可以先用 SQL/内存预筛再点积。
- faiss-node 不建议；usearch 可作为"想要 ANN 索引但又不想动 Postgres"时的备选。

## 4. 检索流水线设计建议

推荐流水线（与 meme_manager/sticker_kit 的实践对齐）：

```
[触发] AI 生成回复文本 R
   ↓
[Query 构造] LLM(R, 近几轮语境) → {"query": "情绪词/用途词/画面词", "intent": "...", "confidence": 0.x}
   （meme_manager: "把已有回复的表达意图压缩为表情图片检索词…只输出 JSON"）
   ↓
[预筛] 关系阶段下限 ≤ 当前关系阶段；风格可按语境偏好加权；blocked_tags 拦截
   ↓
[召回] 方案 A/B/C 三选一（见下）
   ↓
[重排] 可选：bge-reranker-base/large 或 Qwen3-Reranker-0.6B 对 top20 精排
   （StickerSelector 实测档位：embed 召回 20 → rerank → softmax(55) 出 fit_rate）
   ↓
[门槛] score ≥ min_score 且 top1 ≥ margin × top2（sticker_kit _gate_thresholds）
        或 rerank/LLM confidence ≥ 阈值（imagechat_hub 默认 0.45）
   ↓
[兜底] 不过门槛 → 不发图（纯文字）；强命中同分组随机挑一张避免重复
   ↓
[去重] 记录最近 N 张已发，短期内不重复
```

### 方案 A：pgvector + 多语言/中文 embedding（推荐起步）

- **做法**：Postgres 加 `vector` 扩展；`memes` 表加 `embedding vector(512)`（bge-small-zh-v1.5）或 `vector(1024)`；离线脚本把每张图的 `短名+中文重写描述+情绪标签+场景` 拼成文本向量化入库；在线用 LLM 生成的 query 向量化后 `ORDER BY embedding <=> $1`（cosine）取 top 8~20，SQL 里直接带关系阶段/风格过滤。
- **优点**：改动集中、事务一致、运维零新增组件；SQL 过滤天然支持"关系阶段下限"；后续可无痛加 HNSW、halfvec、hybrid（tsvector 关键词 + RRF）。
- **缺点**：Postgres 需装扩展（Windows 裸机要编译或 Docker）；每次查询有一次 DB RTT（同机通常 1~5ms）。
- **成本**：1.9 万张一次性向量化（本地 CPU 几分钟~半小时）；在线仅 query 一条向量。
- **改动量**：中。新增加载/回填脚本 + 查询函数，业务链路把"随机抽 8"换成"向量 top8 + 门槛"。

### 方案 B：LLM 生成中文检索词 + 本地加权计分（sticker_kit 路线，最快落地）

- **做法**：不引入任何向量模型。把现有 JSON 标注规范化成受控词表（情绪 12 枚举直接用；描述让 LLM 离线重写成"情绪词+画面词"中文短语并抽 tags）；运行时 LLM 输出 `{"query":"委屈 低头"}`，Node 内做别名归并 + 字段加权计分（主情绪权重最高，场景/画面词次之，名称最低；每字段取 best 不累加）+ min_score/min_margin 门槛。
- **优点**：零向量基础设施、延迟最低（纯内存计算，<5ms）、完全可控可解释、token 成本只多一次小输出；与现有"情绪标签/场景"字段无缝衔接。
- **缺点**：效果上限受标注词表质量约束；同义改写（用户换个说法）泛化弱于向量；需要先做一轮"描述→受控词"的离线 LLM 重写。
- **成本**：1.9 万张 × 一次轻量文本重写（用现有对话模型即可，成本约几元人民币内，**具体以所用 API 计费为准，未能验证**）。
- **改动量**：小~中。主要是标注重写脚本 + 一个纯函数检索器。

### 方案 C：两阶段 hybrid（向量召回 + 计分/rerank 精排，效果上限最高）

- **做法**：方案 A 召回 top 50 → 再用 sticker_kit 式字段计分（情绪精确命中加权、场景词、关系阶段、近期已发去重惩罚）或 bge-reranker-base 对 50 条精排 → 取 top 8 输出，附分数与理由。
- **优点**：向量负责"语义泛化"（用户没说"委屈"说"心里堵"也能召回），计分/rerank 负责"业务规则与精准度"；meme_manager（FAISS）+ StickerSelector（rerank）+ sticker_kit（计分门槛）三家的优点叠加。
- **缺点**：链路最长，需同时维护向量索引与计分规则；rerank 若用 cross-encoder，CPU 上对 50 条打分会增加 20~100ms（**具体延迟未能验证，需实测**），建议控制在 top20 以内。
- **成本**：方案 A 成本 + reranker 推理资源。
- **改动量**：大。适合方案 A 上线跑通后再迭代。

**推荐节奏**：先 B（一周内可用、立刻消灭"随机抽 8"）或 A（若愿意装 pgvector）；二者不冲突——B 的受控词重写产物正好是 A 的向量文本原料；效果不满意再演进到 C。

### 关于"直接 embed 对话 vs LLM 生成检索词"

- 直接 embed 用户消息/回复原文：零额外 LLM 调用，但长句、称谓、无关细节会稀释向量；meme_manager 明确选择"压缩成检索词"，并保留"直接用回复文本"作为降级开关。
- LLM 生成检索词：多一次轻量生成（几十 token），换来"情绪+对象关系+动作"的精准聚焦，还顺带产出 confidence 供门槛用。**建议采用**（与 meme_manager、sticker_kit、imagechat_hub 三家一致）。
- hybrid（BM25/关键词 + 向量）：在"标签词库+描述"这种半结构化数据上收益明显——关键词负责精确命中"敬礼/比心"这类词表词，向量负责口语泛化。pgvector 官方就建议与 Postgres 全文检索配合（RRF 融合）。规模小，值得做但优先级低于门槛调优。

## 5. 中英描述库的处理建议

现状：描述大部分是英文视觉描述（如 CLIP-style caption），query 是中文。

1. **最优解：离线把英文描述重写成中文检索文本**。用现有 LLM 批量把每张图的英文描述 → "中文短语：主体+动作+情绪+场景"（例如 "a cat waving paw" → "猫 挥手 打招呼"），与中文情绪标签、场景词拼接后作为向量文本。这一步与方案 B 的受控词重写可合并成同一离线任务，一次成本两处收益。
2. **次优解：直接用多语言模型**（bge-m3 / multilingual-e5 / Qwen3-Embedding）对英文描述向量化，中文 query 也能召回。省去重写，但：中文-中文匹配的区分度通常好于跨语言（bge-m3 在 MKQA 跨语言检索上很强，但同语言短文本检索 bge-zh 系仍占优）；且 m3 体积/延迟更大。
3. **不建议**：在线用 LLM 实时翻译 query 成英文再检索——多一跳延迟与失败点；也不建议英/中双索引并行（存储与维护翻倍）。
4. 短名（通常是中文）和 12 个中文情绪标签是现成的高质量中文信号，**务必拼进向量文本**；英文描述仅作为画面细节补充。
5. 参考依据：Sticker820K 的标注结构（描述+OCR 文字+情绪+风格）与本项目字段几乎同构，其做法是为每张图拼接多源文本标注做检索；StickerSelector 则证明"标签文本向量化"在贴纸场景完全够用。

## 6. 学术/工程基准：意图预测 + 跨模态检索 vs 纯文本相似度

- **StickerInt / Int-RA**（arXiv:2403.05427，IEEE TASLP 2025）：指出以往贴纸检索只把贴纸当"当前话语的补充"，而真实场景里贴纸本身可以是"回复"。提出知识增强**意图预测器**把意图信息注入对话表示，再用 relation-aware sticker selector 通过**跨模态关系**选贴纸，在两个数据集上取得 SOTA。数据与代码：https://github.com/HITSZ-HLT/Int-RA （注：仓库 README 仅一句 "The code will be released soon."，实际代码未完整公开——**未能验证其实现细节**）。
- **Sticker820K + StickerCLIP**（arXiv:2306.06870）：82 万中文贴图文本对（描述/OCR/情绪/风格），直接套 CLIP 效果差，专域训练的 StickerCLIP 在文→图检索 mean recall 上绝对提升 66%。说明：**通用图文模型不能直接迁移到表情包域**，域内标注+域内模型/微调很重要。
- **PerSRV**（WWW'25，arXiv:2410.21801）：微信 54.3 万候选贴纸，离线用微调 VLM 生成"类人语义描述"+ 效用评估 + 个性化风格聚类，在线"相关召回 + 个性化排序"。核心可借鉴点：**离线生成高质量中文语义描述 + 在线两阶段**。
- **U-Sticker**（SIGIR'25，arXiv:2502.19108）：22K 用户 / 37 万贴纸 / 830 万消息的大规模多域数据集，面向个性化与时间维度。
- **Sticktionary / StickerQueries**（MM'25，arXiv:2506.01668）：多语言贴纸 query 数据集（1115 英文 + 615 中文），证明"高质量 query 生成"本身就是瓶颈——支持本项目"用 LLM 生成检索词"的路线。
- **PEARL**（EMNLP'25 Findings，arXiv:2509.17749）：把个性化贴纸检索做成生成式（自回归生成贴纸标识符）+ 意图感知学习目标，离线在线均超基线。
- **GSE / Triple-S**（arXiv:2511.04977，2025-11）：提出贴纸视觉语义相似度任务与 905 对人工标注基准，显示现有通用视觉/多模态模型难以捕捉贴纸的细微语义。

**对项目的含义**：学术线一致表明，"理解用户/回复意图（intent）→ 用意图约束跨模态检索"显著优于"裸文本相似度"。工程上对应到本项目 = **LLM 先产出意图/情绪/用途的结构化信号（query + confidence），再检索**；纯向量相似度只能作为召回器，最终排序应叠加业务信号（情绪枚举精确命中、关系阶段、场景模板、去重）。
