## 〇、先回答"这个项目的 AI 对象的根本目的"

通读代码后确认：本项目的 AI 对象的根本目的是 **100% 还原一个真实的人（真人微信式聊天）**。证据：

1. `Prompt构建器.ts` 第一层直接写"你是一个活人在手机上随手打字"；Writer 的系统提示写"像平时微信里真实的两个人在聊天，自然口语化，允许短句、留白和真实停顿"。
2. `语态控制器.ts` 里维护着真人行为基线（"行为类别基线.md 的 2,431 条配对"），并按真人基线重配语态概率；`Prompt构建器.ts` 里有一段 2026-10-18 撤回记录，明确记录了"追问癖 AI 38% vs 真人 10%"这类量化诊断思路。
3. 表情包配置里的发送时机文案（`BiaoQingChuanSongGuiZe`）也全部是真人社交直觉的表述（"接到好笑的事→高概率发""对方刚发→回敬概率大幅提高""严肃求助→禁止发表情包"）。

所以评价表情包机制的唯一标准就是：**它发出来的行为像不像一个真人在微信里聊天**。下面的所有结论都以此为准绳。

## 一、现状机制梳理（代码事实）

当前 AI 发表情包的完整链路是：

```
用户消息 → Director（LLM，输出 JSON 策略，含 biao_qing_yi_tu 意图标签，12 选 1 或 null）
        → 表情载体.panDuanBiaoQingZaiTi()（规则门控）：
            总开关 / 深夜 23-5 点 / 危机关键词 / 关系阶段下限("认识") /
            回敬(对方刚发表情→放行) / 间隔(基于表情密度的期望间隔，含人格系数×关系系数×年龄档×个人偏好哈希)
        → 表情包库.候选系统表情()（按 意图标签 + 风格白名单(年龄档) + 关系阶段下限 过滤后随机抽 8 张）
        → 系统表情.生成表情候选文本()（拼成【表情包候选】块注入 Writer prompt，
            附带 [贴纸:短名] 用法说明 + 发送时机文案）
        → Writer（LLM）在回复文本里写 [贴纸:短名]，位置随意，可以只发图不写字
        → AI回复调度器.发送消息列表()：切分贴纸段 → 上限(每轮1张)校验 → 短名查库 → 落库推送；
            贴纸后短间隔 300-700ms；整轮全贴纸失败时用清洗后文字兜底
```

配套机制：
- 表情包库约 1.9 万张图 + 1.9 万份 JSON 标注（短名/描述/情绪标签/适用场景/启用/风格[黄脸|祝福|日常|梗图]/关系阶段下限），启动扫描 + 指纹变更重扫。
- 最近 6 个已用短名会排除出候选（`zuiJinDuanMing`），防短期重复。
- 对话历史里的表情包以 `[表情包:短名]` 标记渲染给模型，对方发的表情包图片本体会以低细节图像块注入（`AI视觉辅助.ts`），即模型"看得见"用户发的图。
- 每轮最多 1 张（`zuiDaMeiLunZhangShu=1`）。
- 开场白生成 prompt 里允许角色发"表情、emoji"，但开场链路没有接表情包候选注入（开场消息只走文本清洗）。

## 二、问题一：对照 2026 年同类开源项目，现有机制还能怎么优化？

（详细项目清单与证据见 `调研-开源同类项目.md`，此处直接给结论。）

### 结论：能优化，而且空间不小。

先说优势（这些不要动）：
1. **Director 意图模型 + Writer 自选的两段式编排在开源界没有同款**。调研的 12 个项目里，意图判断要么内嵌在回复文本里（ELma 的 `[表情:xx]`、sticker_kit 的末尾标签），要么靠本地小模型分类（SillyTavern 的 28 标签情感分类）。把"发不发/什么情绪"拆成前置小模型、再让 Writer 带着语境和候选自选，是本项目独有的编排，决策质量上限更高。
2. **关系阶段×人格系数×回合间隔×年龄档×个人偏好的多维门控，比所有调研对象都细**。开源项目普遍只有"概率+冷却"两维；把关系阶段下限直接编码进每张表情包的 JSON 标注，是独有的硬门控。
3. 1.9 万张全字段标注库，规模和标注完整度超过所有调研对象。
4. Writer 可以控制贴纸在消息中的位置、可以只发图，这个"位置即语气"的自由度只有 dsh-qqbot 的图组顺序勉强沾边。

短板与优化点（按优先级排序）：

**P0-1：随机抽 8 张没有"语境贴合度"概念，应引入检索/打分兜底。**
现在候选 = 意图标签命中 ∪ 适用场景包含，然后纯随机洗牌取 8 张。1.9 万张库里同一意图下可能有几百张，随机 8 张很可能全是"能用但不贴"的。2026 年的主流做法（meme_manager 的 FAISS 向量检索、StickerSelector 的意图描述→embedding 匹配、sticker_kit 的自研加权计分 min_score/min_margin）都是"先检索排序再给候选"。落地建议：给每张表情包加一个 embedding 向量（用描述+场景+情绪标签做索引），候选改为"意图过滤池内按语义相似度取 top8"，检索不可用时回退现在的随机。sticker_kit 的"第一名领先不足就只发文字不硬塞"思想也值得移植：如果 top 候选匹配分都低，这轮就不给候选。

**P0-2：缺"决策链路诊断"，调参靠猜。**
门控有 8 种拒绝原因（总开关/深夜/危机/关系未到/间隔未到/回敬/门控异常/放行），但没有任何面板能回答"这一轮为什么没发/为什么发了这张"。sticker_kit 有 `/sticker status`、Diana 有事件中心记录"为什么回/为什么没回"。落地建议：把"意图标签值 → 门控拒绝原因 → 候选 8 张短名 → Writer 最终选了谁/弃选"整条链路写入现有的管理员监控通道（`管理员_构建过程` 已有基础设施），运营后台加一个表情包决策页。这是后续一切调参的前提。

**P1-3：没有图库自增长（偷图/收集）通道，1.9 万张静态库会过时。**
所有活跃项目（MaiBot、meme_manager、sticker_kit、smart_imagechat_hub、meme_stealing、dsh-qqbot）都做了"从聊天里自动收集表情包 → 视觉 LLM 打标 → 去重 → 审核入库"。用户在聊天里发的图目前只进了媒体库，没有回流成 AI 可用的表情包候选。落地建议：用户发的 Type=表情 消息，按概率采样进"待审核表情池"，复用现有 `媒体审核` 服务打标（描述/情绪/场景），人工审核通过后并入表情包目录。审核池防投毒是行业标配，必须保留。

**P1-4：没有"用户点名豁免"。**
调研到的项目全部支持"用户说'发个表情包/斗图'就跳过概率与冷却"（meme_manager、sticker_kit 的关键词豁免）。本项目现在用户主动要图时仍会被间隔门控拦。落地建议：在 `panDuanBiaoQingZaiTi` 里加一条：用户最新消息命中"表情包|斗图|来张图|发个图|梗图"等关键词时，跳过间隔与深夜门控（危机门控保留）。

**P1-5：候选注入的 token 预算可以更省。**
sticker_kit 实测过协议成本：完整候选注入每轮固定几百 token。本项目 8 张候选每张都带"描述 | 情绪 | 场景"三段，最长可到 270 字/张。建议候选行只保留"短名 + 情绪标签 + 描述前 40 字"，场景字段砍掉（意图标签已经承担了场景匹配职责），并把候选数从 8 降到 5-6（同类项目普遍 top_k 3-9，5 是常见值；候选太多反而稀释 Writer 的注意力）。

**P2-6：缺同图/同系列冷却的长记忆。**
现在只排除最近 6 个短名。dsh-qqbot 的"同图不连发"、meme_manager 的会话内去重更狠。建议把"最近使用"从 6 个扩到按时间窗（如 24 小时内用过的短名降权而非硬排除），避免 Writer 长期只挑同一张安全牌——真人对自己人也会"这张用腻了换一张"。

**P2-7：开场白/主动关怀链路没接表情包。**
真实数据（见第三部分）显示约 8% 的会话第一句就是表情包，"隔久回来用表情打卡"是真人习惯。开场白生成 prompt 虽然允许"可以有表情"，但链路上没有候选注入，模型只能写 `[xx]` 式文字表情。建议：开场白生成时也走一次候选注入（用"破冰"意图），让角色第一句就可能甩一张梗图。

## 三、问题二：真人到底怎么决定发什么表情包？据此怎么优化 AI？

三条证据线交叉验证：论文（认知机制）、2026 开源工程（实现方案）、本地 13706 条真实微信记录（行为统计）。三者结论高度一致。

### 3.1 真人的决策模型：两阶段 + 五重过滤

**阶段一：要不要发图（模式选择）。** 真人先在"打字/发图/图+字/不回"之间选模式。发图的触发条件按实证重要性排序：
1. **低信息密度、高情感浓度的回合**——问候作息、亲昵调情、日常汇报（吃饭/下班/到家）是表情率最高的前文语境（实测 23.3%/18.7%/18.0%）；Frontiers in Psychology 2026 的微信研究证明享乐与社交满足是核心动机，技术因素无直接效应。
2. **文字表达有社交风险时**——拒绝、示好、自嘲、敷衍，用图兜底（Information, Communication & Society 2025；微笑表情的会话分析研究）。
3. **需要表演情绪强度**——"笑到打鸣""无语到翻白眼"，文字传达不了的强度用夸张图补（emoji 即手势理论，Journal für Medienlinguistik 2026）。
4. **仪式与游戏窗口**——斗图、节日祝福、打卡式问候。
5. **省力接话**——不想打字时一张图就是完整回应。

**阶段二：发哪张（心理库存 → 五重过滤）。** 真人不是全网搜图，而是从"心理库存"（收藏过的、最近用过的、对方发过的、群里流行的）调候选，再过滤：
1. 语义/情绪匹配（图文可以互补但不能冲突到困惑；IEEE TASLP 2025 的贴纸检索研究证明这需要意图理解而非文本相似）；
2. 关系信号校准（对暧昧对象/朋友/长辈候选集完全不同；关系早期用低歧义安全图，稳定后才用圈内黑话梗）；
3. 身份圈层表达（发什么梗=我是什么人；过时梗暴露梗龄，错位玩梗比不玩梗更伤）；
4. 时机与回合位置（同一张图接在自嘲后是共谋，接在认真倾诉后是冒犯）；
5. 库存保鲜度（对同一个人反复发同一张=敷衍；策略是"老梗新用+偶尔上新"）。

**不发图的情形**：对方严肃求助/情绪崩溃/愤怒；自己没接住梗；对方在等明确答复（问句/邀约）；刚发生冲突；深夜情绪脆弱时段。**真人感的很大一部分来自"知道什么时候忍住不发"。**

### 3.2 本地真实语料的关键事实（13706 条实测）

- 表情包占全部消息 12.5%，机主本人 19.1%（约每 5 条 1 张），对方仅 2.8%——**热恋期的机主是高频表情使用者**。
- **表情率全天稳定在 10-18%，深夜不降**——现有代码"23-5 点禁发"与真人行为不符（真人深夜消息总量少，但发的消息里表情占比不掉）。
- **触发语境 top3：问候/作息 23.3%、亲昵 18.7%、日常汇报 18.0%；"哈哈"玩笑反而只有 6.3%**——真人表情包的主要功能是"软性接话"而非"玩梗接梗"。现有配置 `BiaoQingChuanSongGuiZe` 把"接到好笑的事"列为第一触发条件，方向偏了。
- **对方发表情后，真人 80.8% 回文字，只有 4-17% 回敬表情**——现有代码把"回敬"设为无条件放行（绕过间隔门控），回敬倾向过强。
- **连续表情 run≥2 占表情量 17-20%，但 2 张封顶居多**——每轮限 1 张偏保守，真人有"连发 2 张"的习惯。
- **约 30% 的表情前 30 秒有同侧文字**——"先发一句文字、隔几秒补一张图"是真人标志性连招。
- **Type=47 表情 100% 单独成条；另有 12.5% 的文字消息带 [旺柴][捂脸] 式内置 emoji**——"短文字+一个语气 emoji"是固定句式，与图片表情包是两套并行的系统。
- **自定义动画表情占 78%，小黄脸多走文字 [xx] 形态**。
- **关系热度驱动密度**：同一对象热恋期表情率 16.5%，降温期 4.6-6.9%，差 3 倍——现有"关系阶段系数"方向正确，但冷淡 0.4 vs 热恋 2.0 的梯度可以更陡。

### 3.3 据此对现有 AI 机制的优化方案（按优先级）

**P0-A：把"间隔门控"从固定轮距改为"情感浓度驱动 + 基础频率"。**
现在期望间隔 = 密度基数 × 人格系数 × 关系系数 × 年龄档 × 个人偏好，本质是"每 N 轮一张"的均匀节奏。真人（论文 C1、A1 + 本地数据）是**阵发性**的：情绪高峰连发，冷场期纯文字。落地建议：在 Director 的 JSON 输出里加一个字段 `ben_lun_qing_gan_nong_du`（本轮情感浓度 0-100，或直接复用现有 `biao_qing_yi_tu` 非空即视为高浓度），门控逻辑改为：`P(发图) = 基础率(关系阶段) × 浓度加成`，浓度低时即使到了间隔也不发，浓度高时（撒娇/庆祝/感动）允许突破最小间隔。保留每轮上限和总频率上限防刷屏。

**P0-B：修正触发语境权重，让"问候/亲昵/日常汇报"成为表情高发场景。**
在 Writer 的候选块说明（`BiaoQingHouXuanWenAn.daiTiShuoMing`）和 `BiaoQingChuanSongGuiZe` 里，把优先级改为：对方问候作息/说晚安早安 → 高概率配一张软性图；对方撒娇/示好/说想你 → 高概率亲昵图；对方汇报日常（吃了吗/下班了/到家了） → 高概率日常图；对方讲笑话/玩梗 → 中概率（真人此时更多回文字吐槽而非图片）。这条改动的成本极低（只改提示词文案），但直接命中实测数据里最大的偏差。

**P0-C：回敬从"无条件放行"改为"低概率 + 文字优先"。**
实测真人收到表情后八成回文字。建议：对方刚发表情时，仍给候选（保留放行），但在候选块说明里加一句"对方刚发了张图，大多数时候用文字接住它（吐槽/评价/同款情绪），只有觉得这张图特别值得接时才回敬一张"。防止 AI 变成"你一张我一张"的复读机式斗图。

**P1-D：允许"连发 2 张"和"文字+图连招"。**
把 `zuiDaMeiLunZhangShu` 从 1 放宽到 2，并在 Writer 说明里写清："两张图连发适合情绪高潮或斗图，平时一轮一张；也可以先写一句短文字，再单独补一张图（真人最常见的就是这种'先说一句再补图'）"。调度器已支持一段消息内多段切分与贴纸后短间隔，工程上无需改动即可承载；只需放开上限并在提示词里给连招示例。

**P1-E：深夜门控改为"深夜不发搞笑梗图，可发软性图"。**
实测深夜表情率不掉。真到深夜聊天，真人反而更爱用软性/陪伴类图。建议：深夜时段把候选风格过滤为 ['日常','祝福']（排除'梗图'），而不是一刀切禁发。危机门控保留不动。

**P1-F：引入"二人专属表情语"记忆。**
论文 E5（Replika 研究）证明固定互动仪式是人机亲密关系的基础设施；真人情侣之间都有"我们俩才懂的那几张图"。落地建议：新增一张表记录"这张图 + 当时语境 + 双方反应"，Director 策略层在合适时机（对方提起相关话题/想表达特定情绪）优先召回这些"共同记忆图"作为候选置顶。这比任何新图都更能制造"只有我们懂"的亲密感，也是同类项目完全没有的能力（接在现有 Director+Writer 编排上实现成本最低）。

**P1-G：关系早期用"低歧义安全图"，随阶段解锁梗图。**
论文 G5（陌生关系歧义 emoji 误读率高）、D3（梗理解双向盲区）+ 本项目已有"关系阶段下限"标注。建议补一档：'暧昧'以下禁用'梗图'风格（现在 '认识' 阶段就允许梗图，偏早），'暧昧' 解锁梗图，'热恋' 解锁自嘲/沙雕图。同时给 JSON 标注补一个"歧义度"字段（低歧义=情绪直白的抱抱/开心/委屈；高歧义=反讽/圈内梗），早期候选只出低歧义图。

**P2-H：表情包之外，补齐"文字内置 emoji"系统。**
实测 12.5% 的文字消息带 [旺柴][捂脸] 式 emoji，这是与图片表情包并行的另一套系统，且本项目 PROGRESS.md 里已列入计划（微信原生表情码表硬映射）。建议按该计划实施：AI 输出 `[表情名]` → 服务端用微信表情码表（xxk8/wechat-emojis 等）精确匹配 → 渲染；[微笑] 对年轻人设做讽刺语义降权；与图片表情包共享频率预算。

**P2-I：建立表情包效果的闭环评测。**
论文 F1d 警告 LLM 会"表演性堆 emoji"讨好用户，长期被识破。建议：在好感度评判 prompt 里加一个观察维度——用户对带图回复的回应质量（接梗/冷淡/转移话题），按周聚合出"哪类图被接得住"，反哺候选排序。同时利用 P0-2 的决策日志做 A/B：同一语境下"随机候选 vs 语义检索候选"的用户回应差异。

### 3.4 一句话总结

现有机制（Director 意图 + 多维门控 + 候选注入 + Writer 自选）的**骨架是 2026 年开源界最先进的编排**，不需要推倒重来；要补的是三层"真实感"：**选图从随机变检索（P0-1）、节奏从均匀变阵发（P0-A）、语境权重从玩梗变软性接话（P0-B）**，再加回敬降频、深夜放开软图、二人共同图库记忆三个低成本高收益点。全部落地后，表情包行为将与真人数据（12.5% 占比、问候/亲昵/日常高发、80% 文字回敬、2 张连发封顶、阵发节奏）对齐。
